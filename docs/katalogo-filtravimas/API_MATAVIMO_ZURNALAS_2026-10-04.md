# Katalogo facetų API matavimo žurnalas (2026-10-04)

## Matavimo tikslas ir būdas

Tikras `GET /v1/catalog/facets` cache miss / hit HTTP p50 ir p95, naudojant prisijungusią sesiją. Matuojamas visas API atsakymas, o DB cache būklė prieš ir po užklausos patvirtinama tik skaitymo režimu. Užklausos vykdomos nuosekliai, pradedant 12 porų bandomąja serija (po 2 šešioms grupėms), vėliau siekiant 120 porų (po 20 grupei). Atsakymų laikai ir klaidos rašomi į atskirą JSONL failą; prisijungimo žetonas ten nepatenka.

- Scenarijų generatorius ir matuoklis: [catalog_facets_api.py](../../scripts/benchmarks/catalog_facets_api.py).
- Užfiksuoti 240 atsarginių kandidatų: [API_SCENARIJAI_2026-10-04.json](API_SCENARIJAI_2026-10-04.json). Scenarijai paimti iš 12 000 deterministiškai atrinktų realių katalogo produktų; manifestas saugo katalogo versiją, filtrus ir tikslų DB cache raktą.
- Katalogo refresh būklės skaitymo režimo užklausa: [verify_catalog_refresh_read_only.sql](../../supabase/tests/verify_catalog_refresh_read_only.sql).
- Jei reikia tikslesnės cron istorijos, SQL Editor vykdoma tik skaitymo režimo [cron diagnostika](../../supabase/tests/diagnose_catalog_refresh_cron_read_only.sql).
- Vietinė manifestų patikra: `apps/api/src/catalog-benchmark-manifest.test.ts` palygina visų 240 URL API parsavimą su išsaugotais cache raktais.

### 17:27–17:36 UTC prisijungusios naršyklės bandymai

- Naudotojas pažymėjo prisijungusį `https://rinkissaupigiausia.online/` Chrome skirtuką. Sąsajoje matomas `Atsijungti`; prisijungimo žetonas nebuvo skaitomas, kopijuojamas ar įrašomas. Atidarytame puslapyje jau buvo „Filtrų įkelti nepavyko“. Du „Bandyti dar kartą“ bandymai vėl baigėsi ta pačia klaida, todėl **nė viena sėkminga API cache miss/hit pora nebuvo išmatuota**. UI veiksmo laiko negalima laikyti tiksliu HTTP p50/p95.
- Skaitymo režimu `catalog_facets_cache` prieš ir po bandymų turėjo **0** eilučių, įskaitant šakninį `{}` raktą. `service_role` turi `EXECUTE` teisę `catalog_facets_cached`, `catalog_facets` ir `catalog_grouped_size_facets`; `codex_reader` neturi teisės vykdyti šių RPC, todėl per tunelį jie nebuvo kviečiami.
- Vieno puslapio perkrovimo metu, kol vyko 2060 versijos refresh, naršyklė rodė **HTTP 500** produktų `GET /v1/catalog?` užklausai ir bendrą facetų įkėlimo klaidą; facetų HTTP būsena nebuvo matoma. Tuo pat metu DB rodė suteiktą `AccessExclusiveLock` ant `catalog_effective_size_membership_read`. Po 17:35:23 UTC ciklo (`completed_version = requested_version = 2060`, `last_duration_ms = 274641`, būsena `clean`) šis užraktas dingo. Pakartotinai perkrovus puslapį, produktai sėkmingai užsikrovė (rodė **99 889** prekes), bet facetai vis tiek baigėsi „Filtrų įkelti nepavyko“, o cache liko tuščias. Tai atskiria laikiną katalogo skaitymo blokavimą per pilną dydžių refresh nuo dar neišaiškintos facetų cache miss klaidos, kuri kartojasi be to užrakto.
- Iš naršyklės šiuo metu negaunamas facetų HTTP atsakymo tekstas: web `loadFacets()` sugauna klaidą ir rodo tik bendrą pranešimą; naršyklės prieigos įrankis nesuteikia tinklo atsakymų žurnalo ar tiesioginio autentifikuoto `fetch` matavimo. API benchmark nestartuojamas, kol nėra sėkmingo cache miss atsakymo ir tikslaus HTTP matavimo būdo.

**API benchmark nepradėtas.** Prisijungęs skirtukas gautas ir katalogo versijos pasivijo, bet facetų šakninis cache miss šiuo metu baigiasi klaida net tarp refresh ciklų. Pirmiausia nustatyti tikslią API/DB klaidą, atkurti sėkmingą cache miss, tada vykdyti bandomąją ir pilną serijas su atskirais datos bei laiko žymą turinčiais JSONL failais. Užklausų cache įrašai nebus trinami vien dėl matavimo. SQL Editor dar reikia palyginti statinio dydžių cache turinį su materializuota naryste, nes `codex_reader` neturi `SELECT` teisės šiai cache lentelei.

### Vėlesnė šakninio filtro klaidos patikra

- Naudotojas per prisijungusios naršyklės DevTools pateikė `/v1/catalog/facets` atsakymo tekstą: `{"error":"canceling statement due to statement timeout"}`. HTTP būsenos naudotojas dar nepateikė. Taigi šakninio filtro cache miss užklausa viršija DB vykdymo limitą; vien UI pranešimas anksčiau šios priežasties neatskleidė.
- Skaitymo režimu vėliau rasti du sėkmingi `catalog_facets_cache` įrašai su `discountMin = 50` (viename papildomai `colorShades = ["brown"]`), tačiau šakninio `{}` įrašo nėra. Tai parodo, kad bent kai kurie siauresni filtrai gali užpildyti cache. Tiksli šakninės užklausos brangiausia dalis dar nematuota; jos negalima spėti vien iš klaidos teksto.
- Šakninio `catalog_facets()` SQL kūno skaitymo režimo `EXPLAIN (ANALYZE, BUFFERS)` (pagalbinės `catalog_simple_facet` ir išskyrimo funkcijos pakeistos ekvivalentiškais skaičiavimais šiam tuščiam filtrui) užtruko **9 266,508 ms**. `facet_counts` grupavimas turėjo apdoroti **2 171 927** sujungtas eilutes; jo rūšiavimo mazgas užtruko apie **8 736 ms**. Atskirai paruošto facetų read modelio tiesioginis agregavimas užtruko **1 062,488 ms**. Tai SQL kūno dalių, ne HTTP API laikas; DB apkrova ir disko cache gali juos keisti.
- Paruoštos [šakninio filtro migracijos](../../supabase/migrations/20261004170000_fast_unfiltered_catalog_facets.sql) SQL kūno skaitymo režimo planas (dar nepritaikytas VPS) užtruko **3 339,254 ms**; apie **2 106 ms** sudarė `catalog_items_read` skaitymas `premium` bei kainos riboms.
